# 需求挖掘项目需求文档

## 1. 项目目标

修订日期：2026-09-13。本文为目标需求，现有采集与审查程序尚未全部实现。

帮助个人或小团队持续发现产品机会，理解供需缺口，选择值得深挖或做 MVP 的方向，并积累真实反馈。支持发现线索、整理证据、比较机会、选择验证、记录结果、继续或放弃的完整过程。

课程依据：04 的个人抱怨与每日整理；05 的五种市场发现方法；06 的 Alpha 判断；07 的新词站打法。日报、排序、证据格式与状态管理是项目设计，不冒充课程规定。课程案例收益、SEO 效果与风险经验不作为当前事实或结果保证。

本项目不是新闻摘要器，也不是泛泛的趋势日报。它的目标是发现“能做产品”的线索，尤其是：

- 新词刚出现、搜索需求开始上升、供给还没跟上的新词站机会
- Hugging Face Trending 上出现的新模型、新能力、新项目
- 用户公开抱怨暴露出的真实痛点
- 市场里已存在但供给太慢、太贵、太复杂、太烂的供需失衡
- 可以及时行动并承接需求的 Alpha 窗口

明确的非 AI 需求也可进入。项目不自动注册域名、购买服务、投放广告或发布产品，也不自动读取私人聊天和录音。

## 2. 方法论拆解

### 2.1 幸福的方式：收集抱怨

核心原则：不要问用户想要什么，要收集用户哪里不爽。

优先采集这些信号：

- “太难用”“有没有替代品”“求平替”“避雷”“吐槽”
- 竞品评论区的一星/差评
- Reddit、X、Product Hunt、GitHub Issues、插件商店里的重复抱怨
- 工具链断点：导入、导出、迁移、部署、支付、协作、中文/英文支持

筛选问题：

- 这个抱怨是否反复出现？
- 抱怨者是一类人，还是单个偶发个体？
- 现有产品为什么没有解决好？
- 是否能形成一个小工具、模板、工作流、插件或服务？

支持用户随手提交文字、链接或主动提供的转写，不要求先填完整商业分析。保留原话、时间、场景和来源，每日整理问题描述。

补充个人适配判断：是否熟悉或感兴趣，有什么能力与资源优势，是否认识具体有此问题的人，能否接触他们验证。单次抱怨允许记录，重复和付费证据提高关注程度，不设置必须出现三次才能入库的门槛。私人身份信息不默认写入公开日报。

### 2.2 功利的方式：找供需失衡

核心原则：需求已经存在，供给还不够好。

供需失衡类型：

- 搜索词有需求，但 SERP 供给弱
- 新产品/新政策/新平台变化导致用户工作流被打断
- 新技术很强，但普通用户不会用
- 大厂产品太重、太贵、太慢，小团队可以做 20% 聚焦版本
- Fiverr / Upwork 热门人工服务可以被产品化

筛选问题：

- 为什么有人需要它？
- 这些人是谁？
- 他们现在怎么解决，为什么不爽？
- 我能把哪个环节做得更快、更便宜、更简单？
- 这个需求是一次性，还是可以持续滚大？

五种方法分别采集和判断：

| 方法 | 应记录的依据 | 下一步判断 |
| --- | --- | --- |
| 搜索词 | 词群、地区与语言、搜索量或趋势、竞争难度、当前搜索结果、任务意图 | 谁在什么场景搜索、想省掉什么步骤、产品形态、推广与收费路径 |
| 新闻窗口 | 事件原文与时间、受影响人群、被打断或新增的动作、当前替代方案 | 用户是否急于行动、两三天内能否上线、窗口何时可能关闭 |
| 新技术 | 官方发布、模型卡、README、可运行示例、能力与成本变化 | 哪个老任务更快、更便宜或首次可做，谁会尝试，体验层缺什么 |
| 暗影复刻 | 已有产品的用户与付费迹象、重复不满、核心任务、未满足场景 | 保留少量核心功能、补一个重要缺口，通过原型、预付或迁移行为验证 |
| 服务产品化 | 购买或评论证据、交付物、价格、周期、重复步骤 | 哪部分可标准化、人工修正如何保留、混合交付后的成本与收费空间 |

成熟搜索词不要求刚出现或暴涨。支持种子词扩展与词群比较；课程关于美国月搜索量和难度颜色的经验只用于对应打法参考，不成为所有地区、词群和新词的硬门槛。

暗影复刻的“20%”表示聚焦核心任务，不机械计算功能比例。服务产品化允许先自动化部分流程并人工兜底，“60%-80%”不是筛选阈值，挂牌数不能冒充订单数。

### 2.3 Alpha 意识：找窗口期

核心原则：不要问“值不值得做”，要问“这里有没有 Alpha”。

Alpha 判断维度：

- 信息差：是否比中文二手信息更早？
- 行动速度：能否在实际窗口内上线可用方案？
- 判断力：三个月后是否还有人用？需求是否真实？供给是否不足？

Alpha 是跨方法的判断视角，不是独立来源分类。项目新、上榜或来源早都不自动证明存在 Alpha。记录首次出现、当前供给与窗口可能关闭的条件。

仅有概念热度、没有具体任务或能力变化的线索先暂存。长期价值参与投入判断，但不否定一次性现金流机会；短期收益与长期产品潜力分别说明。

### 2.4 新词站：承接高意图搜索

核心原则：新词不是关键词，它首先是一个临时入口。

优先采集：

- 新模型、新产品、新项目、新 API、新开源库
- 搜索需求正在上升但 SERP 结果还弱的新词
- 带有 `generator`、`tool`、`template`、`maker`、`online`、`free`、`alternative`、`tutorial`、`API` 等后缀的任务词
- 官方供给贵、难、慢、不方便的词

新词站判断问题：

- 这个词是否刚出现，热度是否上升？
- 搜这个词的人是想“用”，还是只想“看”？
- 官方供给是否贵、难、慢、不方便？
- 是否能在 48 小时内做出可承接 MVP？
- 背后是否有订阅、credits、转售、服务层、工具层空间？
- 是否有商标/版权风险？

新词站是可关联搜索词、新技术或新闻窗口的专项打法，不另占分类名额。支持提前观察可能出现的词，但预测必须标明，不能编造发布或搜索增长。缺少趋势工具数据时列出可追溯的替代信号与未知事项，不必等待成熟数据才允许深挖。

补充承接与获客判断：主页面交付什么、场景内页如何承接、可用实现积木、试用和支付路径、调用成本、外链及其他推广渠道、所需时间与费用。估算需标明依据，不能声称已经验证。

EMD 是可选方案，不能因名称看起来像开源项目就声称无商标风险，也不把短期运营或跳转当风险豁免。

### 2.5 按类型确定验证时限

- 新词站参考 48 小时内上线真正可承接需求的 MVP，热门窗口可能更短，不能仅用完成调研替代。
- 新闻窗口参考两三天内上线最小方案。
- 其他机会参考课程的七天发布 MVP、获得真实反馈，结合用户资源说明具体动作。

这些是行动参考，不是统一的采集淘汰条件。证据尚少但窗口明确的机会可以建议快速试验，不要求先等大量付费案例。

## 3. 每日采集重点与筛选

不设分类比例、来源名额、每日最低条数或深挖数量上限。新词与新技术保持重点关注，同时覆盖个人抱怨和五种市场发现方法。

先按方法筛选，再合并同一机会的证据，最后比较推荐。方法与来源平台分开记录，一个机会可关联多种方法。相似标题不直接等于同一机会，同一技术服务不同用户任务也可能形成不同机会。

数量与展示规则：

- 采集量、候选量、入库量与摘要展示量分别统计，不以数量判断质量。
- 原始线索、待补证据候选、可推荐机会分开；上下文不足先暂存，不填造事实。
- 完整机会库保留合格内容，手机摘要优先展示重点并提供完整入口；摘要截断不等于淘汰。
- 某方向当天好机会多可以全部保留，不为多样性删好机会，不凑数。
- 长期来源单一时检查采集覆盖，不因当天缺少某来源让日报失败。

## 4. 采集来源

按方法选择来源，优先原始资料。以下是目标覆盖，不代表都已接入：

- Hugging Face Trending
- GitHub Trending
- Product Hunt
- Hacker News
- Google Trends
- 实际搜索结果、Semrush / Ahrefs 等关键词数据（按可用权限接入）
- AI 产品新闻源

需求与交付证据来源：

- Reddit：`r/LocalLLaMA`、`r/SideProject`、`r/SaaS`、`r/ArtificialInteligence`、`r/MachineLearning`
- X / Twitter 公开讨论
- Fiverr / Upwork 热门服务
- 插件商店、SaaS 评论区、GitHub Issues
- 产品价格页、官方 Roadmap、公开客服反馈

中文源作为补充：

- 小红书、知乎、微博、即刻、公众号、行业社群公开内容

用户主动提供的个人记录作为独立入口。来源状态区分已接入、未接入、故障和正常无结果，不把规划能力写成已采集。

证据保留真实摘录、链接或记录标识、发布时间（未知注明）、采集时间。数字、增长、付费、重复抱怨与竞品判断可追溯，同文转载不算独立用户证据。事实、推测、待验证问题分开，抓取失败不能解释成没有需求。

## 5. 判断依据与推荐

本版取消统一五维总分与固定分数阈值，以逐项依据、未知事项和建议动作为主。比较以下内容：

- 需求强度：用户是否明确要解决问题
- 供给缺口：现有供给是否明显不足
- Alpha 时效：是否处于早期窗口
- 个人适配与可执行性：能否接触用户、获得必要资源并及时验证
- 变现潜力：是否能订阅、credits、一次性收费、服务化或导流

- 分发条件与新增信息：如何找到第一批用户，相比历史增加了什么证据

推荐状态：

- 深挖：值得补充调查或快速试验，说明为什么及下一步；不等于已验证值得开发。
- 观察：存在潜力但有关键未知，说明关注什么变化。
- 暂存：上下文不足或暂不相关，保留待补事项。
- 放弃：说明反证、缺少切入条件或其他具体原因。

成熟需求与早期窗口按各自依据判断，证据少不自动否定早期机会。分类和标签服务检索，不控制通过率。课程“舍九取一”用于聚焦实际开发投入，不限制记录或深挖条数。

## 6. 每日报告格式

手机摘要展示新增机会、关注机会的重要变化、推荐理由和运行状态，链接完整日报；无合格机会时正常告知，部分来源失败说明缺口。保持每日节奏，本版不新增高频即时通知。

每条详情包含：

- 线索标题
- 来源和链接
- 发现方法、相关打法与发布时间、采集时间
- 真实摘录与证据、事实结论、商业推测及待验证问题
- 一句话需求
- 用户是谁
- 当前解决办法、个人适配与可接触的目标用户
- 供需失衡
- 可做 MVP
- 实现积木、交付方式、分发路径与预期投入
- 变现方式
- 风险
- 建议状态、理由、下一步动作与建议时限

缺信息允许明确写未知，不要求采集阶段就编出全部商业答案。相同任务可以有相似 MVP，不要求为措辞不同而改变建议。

### 6.1 机会库与复盘

记录机会标识、首次发现、上次推荐、关联证据与新增变化。跨天无新增信息不重复当新发现，有供给变化、新痛点或验证结果时更新。

用户可记录关注、验证中、继续、暂缓、放弃及原因，与系统推荐状态分开。保存验证动作、投入、真实反馈与结果，同日重跑不能覆盖用户记录。放弃一个具体项目不自动屏蔽整个方向。

提供每周可查看的复盘汇总，判断哪些建议推动了验证、哪些推测被推翻、哪些来源持续缺失。

## 7. GitHub 推送策略

每日生成：

- `daily/YYYY-MM-DD.md`
- 追加或更新 `data/opportunities.csv`
- 构建静态页面到 `site/`

每日成果需要推送到 GitHub，便于后续收集和复盘需求。

这里只发布允许公开的内容。私人记录和反馈需与公开产物隔离，不能直接写入公开 CSV、日报或网站；具体存储实现另行设计。

为保证电脑关机后仍能运行，每日任务使用 GitHub Actions 云端定时执行，而不是依赖本地 Codex 自动化。

默认北京时间 08:00，支持手动重跑。采集、发布、微信送达分别记录状态。数量少、来源单一、缺少 HF、没有深挖建议不构成整份失败；单条错误隔离，剩余有效内容继续处理。

全局失败保留诊断并尝试状态通知，不能伪装为正常空日报；微信本身失败保留可查询错误。链接使用已发布结果，未送达不能声称送达。

微信推送：

- 使用 GitHub Actions Secrets 中的 `WECHAT_APP_ID`
- 使用 GitHub Actions Secrets 中的 `WECHAT_APP_SECRET`
- 使用 GitHub Actions Secrets 中的 `WECHAT_OPENID`
- 使用 GitHub Actions Secrets 中的 `WECHAT_TEMPLATE_ID`
- 每天生成 GitHub Pages 日报链接后，通过微信公众号测试号模板消息推送

提交范围：

- 允许提交：`daily/`、`data/`
- 允许提交：`site/`
- 可选提交：`README.md`、`docs/`、`templates/`、`scripts/`、`.github/workflows/`
- 禁止提交：04、05、06、07 等课程原文 Markdown、密钥与私人记录

提交信息格式：

```text
daily: add opportunities YYYY-MM-DD
```

执行策略：

```bash
git add daily data site
git commit -m "daily: add opportunities YYYY-MM-DD"
git push
```

注意：不要使用 `git add .`，避免把课程原文推送到 GitHub。

如果当前仓库尚未配置 GitHub remote，则每日任务仍应生成本地日报，并在日报末尾记录推送未完成的原因。

## 8. DeepSeek 接入计划

第一版不使用模型，先以规则采集和人工可读报告为主。

这是当前实现状态，不代表已满足本版需求。后续模型名称使用 `DEEPSEEK_MODEL=deepseek-flash`，配置不代表已经接入或调用成功。

第二版可接 DeepSeek 做：

- 摘要
- 去重
- 证据提炼与判断依据
- 新词变体扩展
- MVP 方案生成

模型不能补造搜索量、订单、评论、用户身份或竞品结论。外部内容作为资料，不作为执行指令。模型不可用时保留证据并说明分析未完成。

安全规则：

- API key 不写入代码
- 使用环境变量 `DEEPSEEK_API_KEY`
- `.env` 必须加入 `.gitignore`

## 9. 验收与实施范围

- 方法与来源分开，五种方法和个人输入各有判断要求，未接入能力明确标示。
- 每个推荐可追溯证据，事实、推测与未知可辨认，不以热度证明需求。
- 无配比、最低条数或深挖数量门槛；正常空结果与故障能区分。
- 验证时限匹配机会类型，短期现金流和长期产品均可保留。
- 跨天更新可追溯，重跑不覆盖用户反馈，公开内容不包含私人信息。
- 日报可阅读、发布与推送状态可查，错误可定位。

第一阶段优先修复既有来源的真实证据、分类判断、去重、日报与失败状态，支持最小个人文字记录和手动反馈；后续补搜索、竞品、服务证据接入与复盘汇总。阶段未完成项明确说明，不视为已交付。

效果以用户认可的推荐、实际开展的验证和判断修正来复盘，不以日报条数或深挖占比衡量。数值目标在实际使用后确定。
