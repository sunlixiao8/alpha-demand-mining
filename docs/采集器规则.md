# 每日采集器规则

## 总原则

修订日期：2026-09-13。本文配套《需求文档》，描述目标行为；现有采集与审查程序尚未全部按本版实现。

采集服务于发现供需失衡和选择验证，不设分类比例、来源名额、每日最低条数或深挖数量上限。原始线索、待补证据候选和可推荐机会分开。

完整原始池经过去重后保留。规则按每种方法的强信号评分并统一比较，单次最多取 40 条公开候选给 DeepSeek 分析，不按分类凑数。技术资料的篇幅和功能词不等于需求强度；明确抱怨、反复任务、订单、付费、迁移行为和多条可追溯讨论应获得更高优先级。日报最多展示 20 条“深挖/观察”，这只是阅读上限。

日报不是“链接堆砌”，而是商业决策简报。每条线索都要回答：

- 结论：今天要不要深挖？
- 证据：我凭什么认为它有机会？
- 为什么现在：窗口期在哪里？
- 用户是谁：谁会真的痛？
- 真实需求：用户要完成什么动作？
- 供需失衡：现有方案哪里慢、贵、难、差？
- 切入角度：个人/小团队从哪里切？
- MVP：按实际窗口，何时能上线什么可用方案？
- 分发路径：第一批用户从哪里来？
- 变现方式：怎么收钱？
- 风险：为什么可能不成立？
- 下一步验证：明天具体做什么？
- 置信度：证据够不够？
- 个人适配：是否熟悉这个问题，能否接触具体用户？
- 实现与投入：哪些积木可用，交付和推广需要什么资源？

事实、推测和未知分开，缺信息允许说明，不用模板补造答案。记录真实摘录、来源链接或记录标识、发布时间（未知注明）与采集时间。采集提示语和模型建议不能充当原始证据。

自动采集的公开网页摘录允许发送 DeepSeek；私人记录和手动导入内容不发送。推荐条目先展示英文逐字原文，下一行展示中文翻译。引用必须能在保存的原文中逐字核对，中文翻译字段必须包含中文；失败时只隔离具体条目。

采集时优先问：

1. 这里有没有新词？
2. 这里有没有高意图搜索？
3. 这里有没有 Hugging Face / GitHub 新能力？
4. 用户是否正在抱怨？
5. 供给是不是太慢、太贵、太复杂、太难用？
6. 能否在这个机会的实际窗口内验证和交付？

## 按方法筛选

个人抱怨加五种市场方法是发现框架。来源平台单独记录，新词站是可关联多种方法的打法，不另占名额。具体机会不按类别固定高低优先级。

### 搜索词机会

检查词群、地区和语言、搜索量或趋势、竞争与实际搜索结果、任务意图、产品形态、推广与收费路径。支持种子词扩展，成熟词无需刚出现。课程的搜索量参考不设为所有词和地区的下限；无数据写明未获取。

### 新词站专项检查

强信号：

- 新模型、新能力、新产品刚发布
- 词本身开始被反复提及
- 用户在搜“哪里用”“free”“generator”“tutorial”“alternative”
- 官方入口不方便、地区受限、价格高、部署麻烦

必须标记：

- 是否适合 EMD
- 是否有商标风险
- 是否适合做工具页、教程页、替代入口、API 代理、资源导航
- 48 小时内能否上线真正可承接需求的 MVP，窗口是否要求更快
- 主页面、场景内页、可用交付能力、试用与支付、外链与推广投入

尚无趋势数据时保留替代证据并标明未知，不编造增长，也不要求等成熟数据才允许深挖。预测必须标明。EMD 可选，不能以短期运营或跳转作为风险豁免。

### 新技术机会

优先官方发布、模型卡、README 和可运行示例，Hugging Face Trending 是重点来源之一，不是必选配额。

强信号：

- 新模型能力明显改变某个任务成本
- Demo 很强但普通用户不易用
- 开源项目缺少产品化包装
- 评论区、社区、模型卡里能看到具体使用场景

必须转译成：

- “谁会用”
- “用来完成什么任务”
- “现有方案哪里麻烦”
- “能不能做一个更简单的 Web 工具”
- 哪项能力或成本发生变化，可用接口、实现和交付条件是什么

热度不自动证明需求，不能仅凭项目名称推断不存在的功能。早期证据少可以建议小规模试验，需说明未知。

### 新闻窗口

强信号：

- 平台政策、模型发布、产品限制、地区限制、价格变化
- 用户工作流被打断
- 两三天内可以做迁移、转换、教程、生成、代理、聚合工具

保留事件原文与时间，说明受影响用户、具体动作和窗口关闭条件。一次性需求可以成立，不因缺少订阅空间淘汰。

### 个人与社区抱怨

强信号：

- 多个独立记录反复出现同类抱怨，次数可追溯；转载不算独立用户
- 用户主动求替代品
- 用户已经为旧方案付费但仍不满意

支持用户主动提交文字、链接与转写；保留场景、现有办法、个人熟悉程度和可接触用户。单次抱怨可暂存，不必凑足三次。私人内容不默认公开。

### 暗影复刻

检查原产品的用户和付费迹象、重复不满、核心任务、准备保留的少量功能及关键差异点。通过原型、预付或实际迁移行为验证；不默认复制完整产品，也不把“20%”机械用作比例。

### 服务产品化

强信号：

- Fiverr / Upwork 服务订单多
- 交付物标准化
- 存在可标准化的重复流程，允许人工修正与混合交付

核查购买证据、价格、周期、自动化成本和人工部分。挂牌数量不等于成交数量，“60%-80%”是课程参考，不是入选阈值。

## 排除规则

暂不推荐或隔离处理：

- 抓取失败或链接不可访问时保留故障状态，暂存待补查，不解释为无需求
- 没有描述、没有上下文、无法判断用户任务
- 只有热闹，没有明确动作
- 纯融资、纯大厂战略、纯观点争论
- 用户只想“了解一下”，没有工具/服务意图
- 明显高法律风险且无法转向正常产品
- 缺少必要资源、无法提出个人可执行切入点，记录具体原因

非 AI 痛点不因缺少关键词被过滤。损坏或伪造的证据不能作为事实发布。新词参考 48 小时可承接 MVP、新闻参考两三天，其他机会参考七天发布 MVP 获得反馈；不是统一采集门槛。

谨慎标记：

- 商标词 EMD
- 医疗、金融投资、成人、灰产
- 依赖不可控封号/绕限制路径的产品

## 自检规则

生成日报前必须自检：

- 切入角度与 MVP 是否对应真实任务；同类任务允许相似方案，重复机会应合并
- 是否保留了原始信号，方便人工复核
- 是否有明确分发路径，而不是只说“做个工具”
- 是否能支持商业决策：深挖、观察、丢弃
- 是否把推测冒充事实、用替换名称的模板忽略了项目差异

目标自检要求如下；`scripts/audit_report.py` 尚需另行改造：

- 证据是否可追溯，数据是否一致，事实、推测和未知是否分开
- 任务与建议是否对应，推荐理由和下一步是否明确
- 链接格式与访问状态分别记录，不能仅凭格式宣称可访问
- 是否有私人信息泄露，是否把同文转载算作独立证据

数量少、来源单一、缺少 HF 或没有深挖建议均不构成整份失败。单条错误隔离修正或暂存，其余有效内容继续处理。全局故障保留诊断并尝试状态通知，不伪装成正常空结果；微信不可用时保留可查错误。

## 每日排序规则

先按方法判断，合并同一机会的多源证据，再比较需求依据、供给缺口、个人适配、窗口紧迫性、获客与收费条件和新增信息。不再用统一五维总分及固定阈值。

- 深挖：值得调查或快速试验，写明原因和动作，不等于已验证成功。
- 观察：有潜力但有关键未知，说明要等什么变化。
- 暂存：上下文不足或暂不相关，保留待补事项。
- 放弃：说明已知反证或缺少切入条件。

证据扎实的成熟需求与证据尚少的早期窗口按各自依据判断。推荐条数取决于内容，不改标签满足规则。手机摘要只影响展示，完整机会库保留其余合格内容。

## 历史与复盘

记录首次发现、上次推荐、新增证据和窗口变化，跨天无新增信息不重复当作新发现。同一技术的不同用户任务可分别记录。

用户行动状态与系统建议分开，保存验证动作、投入、反馈、继续或放弃理由，重跑不能覆盖用户记录。定期检查推荐是否推动实际验证，采集是否有覆盖缺口，不以配额修正结果。
